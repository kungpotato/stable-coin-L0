คำนำ

หนังสือเล่มนี้มาจากไหน

หนังสือเล่มนี้เรียบเรียงจาก workshop ที่ตั้งโจทย์ไว้ข้อเดียวคือ "อยากเข้าใจ LayerZero จริงๆ" แต่เมื่อทำไปเรื่อยๆ โจทย์ก็ขยายเป็น "เอาเชนของเราเอง (potato-chain) มาเชื่อมกับเชนอื่น แล้ว bridge ทั้ง native coin และ stablecoin ให้ได้" และจบที่คำถามว่า "ถ้าจะใช้จริง ต้องทำอะไรอีก"

ทุกตัวเลขในเล่มวัดจากเชนจริงทั้งหมด ไม่ว่าจะเป็นค่า gas, เวลาที่ message ใช้เดินทาง, ยอดเงินที่ถูกดูดออกจาก lockbox หรือจำนวนวันที่ IBC client หมดอายุ แต่ละขั้นตอนมีคำสั่งที่รันซ้ำได้ใน workshop-layerzero.xlsx และโค้ดทุกบรรทัดอยู่ใน commit ขนาดเล็กตามแนวทางของหนังสือ Accelerate

เล่มนี้ไม่ใช่คู่มือแทนเอกสารทางการของ LayerZero แต่เป็นบันทึกว่าเมื่อลงมือทำจริงแล้วเจออะไร หลายบทเรียนที่สำคัญที่สุดไม่ได้มาจากตอนที่ทุกอย่างผ่าน แต่มาจากตอนที่มันพัง เช่น deploy บน Sepolia แล้ว out of gas เพราะเชนเปลี่ยนกฎ gas, message ค้างเพราะ config สองฝั่งไม่ตรงกัน, เครื่องมือตรวจจับที่ถูกหลอกได้ และสคริปต์ที่รายงานว่า "ผ่าน" ทั้งที่ยังไม่ได้ทำอะไรเลย

สำหรับใคร

LayerZero ส่ง "ข้อความ" ไม่ได้ถือ "เงิน"

ความเข้าใจผิดที่พบบ่อยที่สุดคือคิดว่า LayerZero เป็น bridge บทนี้พิสูจน์ด้วยยอดเงินบนเชนว่ามันไม่ใช่ และอธิบายว่าทำไมเรื่องนี้ถึงเปลี่ยนวิธีคิดเรื่องความปลอดภัยทั้งหมด

เป้าหมายอธิบายได้ว่า LayerZero เป็น messaging layer และไม่ถือเงินผู้ใช้
ต้องเตรียมพื้นฐาน blockchain และอ่านเคส bridge hack (Ronin, Wormhole, Nomad)

บทเรียน

ความปลอดภัยของเงินเป็นความรับผิดชอบของเจ้าของ OApp ทั้งโค้ดของ OApp, การเลือก DVN, การตั้ง config และ control ฉุกเฉิน LayerZero ให้เครื่องมือมา แต่ไม่ได้ตัดสินใจแทน

1.2 ใครทำอะไรได้ และทำร้ายเราได้แค่ไหน

วิธีคิดเรื่องความปลอดภัยที่ใช้ได้ผลคือถามทีละผู้เล่นว่า "ถ้าคนนี้เป็นฝ่ายร้าย จะทำอะไรได้" คำตอบด้านล่างไม่ได้มาจากเอกสารอย่างเดียว ทุกแถวมีบทที่ลองทำจริงใน lab

เหตุการณ์เกิดอะไรขึ้นประเภทใน lab ของเรา
Ronin

~$727K ที่ออกไปได้		ผู้โจมตีเข้าถึงฐานข้อมูลของ service ที่ทำงานรองรับ bridge แล้วใช้ช่องโหว่ใน logic การประมวลผล message สร้างคำสั่ง mint ปลอม 10M CYS บน BNB Chain เริ่มเทขายภายใน 5 นาที ย้าย 306.6 ETH ออกไป Ethereum แล้ว blacklist มาถึงที่นาทีที่ 76 (ข้อมูลเบื้องต้น ยังไม่เปิดเผยว่าใช้ bridge แบบไหน)ข้อมูล off-chain ที่ผู้ยืนยันเชื่อถูกแก้ไขผลเหมือน drill บท 3 ป้องกันด้วยผู้ยืนยันที่อ่านเชนต้นทางเองจากแหล่งข้อมูลที่อิสระ (บท 3.6, 12) และเพดาน mint ขาเข้า ที่เพิ่มหลังเหตุการณ์นี้ (บท 6.6)

ทุกเหตุการณ์จบแบบเดียวกัน คือ mint หรือถอนเงินได้โดยไม่มีของจริงรองรับ และสิ่งที่ช่วยได้ทุกกรณีมีสี่อย่าง

  1. ผู้ยืนยันหลายรายที่อิสระต่อกัน ทั้งคนละองค์กร คนละ key และคนละ codebase
  2. เพดานความเสียหายต่อช่วงเวลา (rate limit) เพื่อให้เสียได้ไม่เกินที่รับได้ ระหว่างที่ยังไม่มีใครรู้ตัว
  3. ตรวจ invariant แบบ real-time ว่ายอดที่ mint ไม่เกินยอดที่ lock
  4. สวิตช์หยุดฉุกเฉิน (pause หรือ BlockedMessageLib)

สี่ข้อนี้คือโครงของภาค 1 ทั้งหมด: บท 3 ว่าด้วยข้อ 1, บท 6 ว่าด้วยข้อ 2 และ 4, บท 8 ว่าด้วยข้อ 3 และการรับมือเมื่อทุกอย่างล้มเหลว

1.4 ข้อค้นพบ: เรายังพึ่ง default อยู่โดยไม่รู้ตัว

ระหว่างเขียนตารางบทบาท เราพบว่า OApp ของเราตั้ง DVN เองแล้ว แต่ send library และ receive library ยังใช้ default ของ endpoint แปลว่าถ้าเจ้าของ endpoint เปลี่ยน default library ข้อความของเราจะไปวิ่งผ่าน library ใหม่ทันทีโดยเราไม่ได้ตัดสินใจ

กับดัก

"ตั้ง config เองแล้ว" ไม่ได้แปลว่าไม่ได้พึ่ง default เลย config ของ OApp มีหลายชั้น (library, ULN config, executor config) และชั้นที่ไม่ได้ตั้งจะ fallback ไปที่ default เสมอ ทางแก้คือ pin library ด้วย setSendLibrary และ setReceiveLibrary ซึ่งทำในบท 8

สรุปบทที่ 1

  • LayerZero เป็น messaging layer ส่วนเงินอยู่ใน OApp ที่เราเขียน
  • DVN ที่ครบ quorum มีอำนาจสูงสุด ส่วน executor ทำได้แค่เรื่อง liveness
  • bridge hack ทุกเคสคือ "mint โดยไม่มีของรองรับ" ป้องกันด้วยผู้ยืนยันที่อิสระ, rate limit, invariant และ pause
  • ต้องตรวจทุกชั้นของ config ว่ายังพึ่ง default ตรงไหน

ชีวิตของ message หนึ่งตัว

ถ้าไล่ได้ว่า message หนึ่งตัวผ่านอะไรบ้าง ตั้งแต่ถูกส่งจนไปถึงปลายทาง ทุกบทหลังจากนี้จะเข้าใจง่ายขึ้นมาก เพราะทุกปัญหาที่เจอคือ message ที่ติดอยู่ที่ขั้นใดขั้นหนึ่ง

เป้าหมายไล่ lifecycle ได้: send → DVN verify → commit → lzReceive
ต้องเตรียมเข้าใจ event/log ของ EVM, เปิด LayerZero Scan ได้
ผลลัพธ์relay ด้วยมือได้ทุกขั้น (บท 9, 11) แล้วจึงทำให้อัตโนมัติ (บท 12)

2.1 ฝั่งต้นทาง: จบที่ event

เมื่อ OApp เรียก _lzSend(dstEid, message, options, fee, refundAddress) สิ่งที่เกิดขึ้นบนต้นทางมีแค่ใน tx เดียว

  1. Endpoint เพิ่ม outbound nonce ของ path (OApp ต้นทาง, EID ปลายทาง, peer ปลายทาง) แล้วสร้าง packet ซึ่งมี GUID ไม่ซ้ำกัน
  2. SendUln302 (send library ตาม config ของ OApp) คิดค่าธรรมเนียมของ DVN ทุกตัวและ executor แล้วมอบงานให้แต่ละตัว ซึ่งเห็นได้จาก event JobAssigned ที่ contract ของ DVN
  3. emit PacketSent(encodedPacket, options, sendLibrary) ซึ่งเป็นสิ่งเดียวที่ off-chain worker ใช้รู้ว่ามีงาน

ค่าธรรมเนียมทั้งหมดจ่ายครั้งเดียวบนต้นทาง (quote แล้วส่ง msg.value) ส่วน options คือสิ่งที่ผู้ส่งขอ เช่น "ให้ executor ใช้ gas 100,000 ตอนเรียก lzReceive" ซึ่งกลายเป็นต้นเหตุของปัญหาในบท 4

2.2 ระหว่างทาง: งานของ off-chain worker

DVN ดู event PacketSent แล้วรอให้ block ของ packet ผ่านจำนวน confirmations ที่ config กำหนด (กันการ reorg) จากนั้นเรียก verify(header, payloadHash, confirmations) บน ReceiveUln302 ของปลายทาง DVN แต่ละตัวเซ็นเอง ไม่รับข้อมูลต่อจาก DVN อื่น

Executor รอจนครบ quorum ของ DVN แล้วทำสองอย่างบนปลายทาง คือเรียก commitVerification ให้ endpoint บันทึก payload hash ที่ผ่านการยืนยันแล้ว และเรียก lzReceive เพื่อส่ง message ให้ OApp

ทุกคนเป็น executor ได้

หลังจาก DVN ยืนยันครบแล้ว ใครก็เรียก commitVerification และ lzReceive ได้ เพราะ endpoint ตรวจ payload กับ hash ที่ยืนยันแล้วเสมอ ความจริงข้อนี้ช่วยเราไว้สองครั้ง คือกู้ message ที่ FAILED บน testnet (บท 4) และกู้ message ที่ค้างตอน worker ปิด (บท 12)

3.2 ตั้งฉากการทดลอง

การปลอม message จะกิน nonce ของ path ไปถาวร เราจึงไม่ทดลองกับ POTATO หรือ USDC แต่สร้าง token ทิ้งได้สองชุด

  • DEMOWEAK: ไม่ตั้ง security เอง จึงใช้ default คือ DVN-A ตัวเดียว
  • DEMOSAFE: ตั้งให้ต้องผ่าน DVN-A และ DVN-B ซึ่งเป็น operator คนละคน ใช้ key คนละดอก

สมมติฐานของการโจมตีคือ key ของ DVN-A หลุด ซึ่งเป็นเหตุการณ์แบบเดียวกับ Ronin

3.3 การโจมตี DEMOWEAK

  1. baseline โอน DEMOWEAK จริง 100 จาก anvil ไป potato ให้มีของจริงอยู่ใน lockbox ผล: locked 100 = minted 100 ✅
  2. ปลอม mint สคริปต์ ForgeMint.s.sol ใช้ key ของ DVN-A สร้าง packet ปลอมว่า "anvil lock ไว้ 1,000,000 แล้ว" จากนั้น verify, commit และ lzReceive เอง 
    PRIVATE_KEY=$DVN_KEY ASSET=DEMOWEAK AMOUNT=1000000 \
  forge script script/ForgeMint.s.sol --rpc-url http://localhost:18545 --broadcast
    ผล: ผู้โจมตีได้ 1,000,000 DEMOWEAK.lz โดยไม่มีอะไรถูก lock และ check-supply.sh ขึ้น ❌ FORGED
  3. ดูด lockbox ผู้โจมตีส่ง 100 จากของปลอมกลับไป anvil ระบบทำงานถูกต้องทุกอย่าง คือ burn บน potato แล้ว unlock บน anvil ผล: lockbox 100 → 0 ผู้โจมตีได้ DEMOWEAK จริง 100 ส่วนผู้ใช้จริงถือเหรียญที่ไม่มีหลักประกันเหลืออยู่

ความเสียหายจริงของ bridge hack ไม่ได้อยู่ที่เหรียญปลอมที่ mint ออกมา แต่อยู่ที่ของจริงใน lockbox ที่ถูกถอนออกไปด้วยเหรียญปลอม เพราะเหรียญปลอมกับเหรียญจริงบนปลายทางแยกจากกันไม่ได้

3.4 การโจมตี DEMOSAFE

ก่อนโจมตีเราเปิด DVN-B worker ซึ่งเป็น operator คนที่สอง worker ตัวนี้ยืนยันเฉพาะงานที่ถูก assign ให้ตัวเองเท่านั้น (มันข้ามข้อความเก่า 42 ตัวเพราะไม่เคยถูก assign) แล้วทดสอบการโอนปกติก่อน เพื่อยืนยันว่า config ที่เข้มขึ้นไม่ทำให้ของจริงพัง (delivered ใน 7 วินาที โดยทั้ง A และ B verify)

จากนั้นใช้การโจมตีเดิมทุกอย่าง ผลคือสคริปต์รายงาน BLOCKED: requires DVNs: 2 และถ้าบังคับให้ส่งต่อ (FORCE=true) endpoint จะ revert ด้วย LZ_ULN_Verifying() ผู้โจมตีได้ 0 และ invariant ยัง ✅

3.5 config สองฝั่งต้องตรงกัน

การทดลองที่สองในบทนี้ตอบคำถามว่า "ถ้าฝั่งส่งกับฝั่งรับตั้งไม่เหมือนกันจะเกิดอะไร" เราตั้งให้ฝั่งส่งบน anvil assign งานให้ DVN-A ตัวเดียว แต่ฝั่งรับบน potato ต้องการ A + B

  1. ส่ง 10 DEMOSAFE ผล: ไม่ถึงหลัง 90 วินาที DVN-A verify แล้ว แต่ DVN-B บอกว่า "not assigned, skip" ส่วน executor รอไม่สิ้นสุด และ check-supply ขึ้น ⏳ 10
  2. แก้ config กลับให้ตรงกัน ผล: ยังค้างอยู่ เพราะการแก้ config มีผลกับ message ใหม่เท่านั้น ไม่ได้ย้อนไป assign งานเก่าให้ DVN-B
  3. ให้ DVN-B attest เอง operator ตรวจ packet บนต้นทางด้วยตัวเองแล้วเซ็น (ไม่รับข้อมูลต่อจากใคร)

3.6 "อิสระ" แปลว่าอะไร

DVN สองตัวที่รันโดยทีมเดียวกัน ใช้ server เดียวกัน หรือ key อยู่ใน vault เดียวกัน ไม่ได้ปลอดภัยกว่า DVN ตัวเดียวมากนัก ความอิสระที่ต้องการมีหลายมิติ

  • องค์กร: คนละบริษัท ไม่มีใครสั่งอีกฝ่ายได้
  • key management: คนละ HSM คนละขั้นตอนการเข้าถึง
  • codebase: ลดโอกาสที่ bug ตัวเดียวจะทำให้ทุกตัวยืนยันผิดพร้อมกัน (บทเรียนจาก Wormhole)
  • แหล่งข้อมูล: อ่าน RPC ของต้นทางจากคนละ node และต้องอ่านจากเชนเอง ไม่ใช่จากฐานข้อมูลกลาง (เคส Cysic ในบท 1.3)

บน testnet เราเลือก LayerZero Labs + Nethermind สำหรับ messaging และ LayerZero Labs + Horizen สำหรับ lzRead

สรุปบทที่ 3

  • default ของ endpoint ใช้ DVN ตัวเดียว ทั้งใน lab และบน testnet ทางการ
  • path ที่มี DVN ตัวเดียว: key หลุดหนึ่งดอก = mint ได้ไม่จำกัดและดูด lockbox ได้
  • path ที่ต้องผ่าน 2 DVN อิสระ: การโจมตีเดียวกันถูกบล็อกที่ LZ_ULN_Verifying
  • config ฝั่งส่งและฝั่งรับต้องตรงกัน ไม่งั้น message ค้าง และแก้ config ทีหลังไม่ช่วย message เก่า
  • optionalDVNCount = 0 คือ "ใช้ default" ส่วน "ไม่มี" ต้องเป็น 255

คำถามทบทวน

ทำไม DEMOSAFE ยังถูก check-security ตั้งธงว่าเสี่ยงหลังจาก A หลุด ทั้งที่การโจมตีถูกบล็อก

เพราะ DEMOSAFE ยังเชื่อ DVN-A ซึ่งหลุดไปแล้ว ตอนนี้ความปลอดภัยของมันเหลือเท่ากับ DVN-B ตัวเดียว ถ้า B หลุดอีกดอกก็โดนเจาะ จึงต้องย้ายไปใช้ B + C (บท 8)

Control ของ stablecoin

bridge ของ stablecoin ต่างจาก bridge ทั่วไป เพราะผู้ออกเหรียญต้องคุมได้ว่าเงินไปไหน หยุดได้เมื่อมีเหตุ และไม่ให้ address ที่ถูก sanction ใช้ได้ บทนี้ออกแบบ control ห้าอย่างโดยไม่ให้ message ค้าง

เป้าหมายมี rate limit, เพดาน mint ขาเข้า, pause, blacklist และ supply invariant ข้ามเชน
ต้องเตรียมบท 5, AccessControl/Pausable, ข้อกำหนด compliance
ผลลัพธ์USDC v2 ที่มี control ครบ, unit test 15/15, ADR 0003 และ 0005

6.1 Rate limit: เพดานความเสียหาย

rate limit จำกัดยอดที่ส่งออกได้ต่อเชนปลายทางต่อช่วงเวลา ใน lab ตั้งไว้ 10,000 USDC ต่อ 60 วินาที ถ้า DVN, executor หรือ key ถูกเจาะ ความเสียหายต่อ window จะไม่เกินเพดานนี้ ทำให้มีเวลาให้ alert และ pause ทำงาน

  • นับเฉพาะขาออก (_outflow) ส่วนขาเข้า (_inflow) คืนโควตาให้ path เดียวกัน
  • เกิน limit จะ revert ตอนส่ง ไม่ใช่ตอนรับ ไม่มี message ค้าง (step 14.7: ส่ง 15,000 ได้ RateLimitExceeded และ supply ไม่เปลี่ยน)

6.2 Pause: สวิตช์ฉุกเฉิน

  • ขาส่ง: ส่งไม่ได้ revert ด้วย EnforcedPause
  • ขารับ: message ที่มาถึงตอน pause จะรออยู่ที่ executor ไม่หาย และ delivered เองหลัง unpause (step 14.8: ⏳ 50 ระหว่าง pause แล้ว delivered 23 วินาทีหลัง unpause)

pause จึงเป็นเครื่องมือที่ปลอดภัยที่จะกดทันทีที่สงสัย เพราะยกเลิกได้และไม่ทำให้เงินหาย

6.3 Blacklist: แยกหน้าที่ออกจาก owner

ใน ADR 0003 เราตั้งใจไม่ใส่ blacklist เพราะคิดว่า issuer blacklist บน home chain เองก็พอ แต่ blacklist บน home หยุดได้แค่บน home ส่วน USDC.lz บน potato ยังโอนได้อิสระ ADR 0005 จึงเพิ่ม blacklist ในทุก leg ด้วยหลักการเหล่านี้

  • role blacklister แยกจาก owner: owner แต่งตั้ง blacklister ได้ แต่ blacklist เองไม่ได้ (step 6.5: owner ได้ NotBlacklister) เหมือนการแยกหน้าที่ของ Circle
  • address ที่ถูก blacklist bridge ออกไม่ได้ และบน UsdcOFT โอนเข้าหรือออกไม่ได้เลย เพราะบล็อกที่ _update

6.4 Quarantine: ทำไมห้าม revert ตอนรับ

คำถามที่ยากที่สุดของบทนี้คือ "ถ้ามีคนส่งเงินข้ามเชนมาให้ address ที่ถูก blacklist จะทำอย่างไร" คำตอบที่ดูง่ายคือ revert ใน lzReceive แต่นั่นทำให้ message ค้างตลอดไป และ nonce ถัดไปอาจติดอยู่ข้างหลังด้วย (เราเห็นผลของ message ที่ค้างถาวรแล้วในบท 8 และ CreditFailed ในบท 13)

ทางที่เลือกคือ quarantine: message ถึงตามปกติ แต่เงินถูกกักไว้

  • ฝั่ง potato (OFT): mint เข้าตัว contract เองแล้วบันทึกใน quarantined[to] เหรียญยังมีหลักประกันแต่ใช้ไม่ได้
  • ฝั่ง anvil (adapter): เหรียญอยู่ใน adapter ต่อ แต่ถูกบันทึกว่ากักไว้ และ check-supply ต้องหักออกจากยอด lock เพราะไม่ได้เป็นหลักประกันให้ supply บนเชนอื่นแล้ว
  • ปล่อยเงิน ด้วย releaseQuarantined(to, payee) เป็นการตัดสินใจของ owner เท่านั้น จ่ายคืนเจ้าของเมื่อปลด blacklist หรือจ่ายให้ issuer ตามคำสั่งศาลก็ได้ แต่ห้ามจ่ายให้ address ที่ยังถูก blacklist
// StablecoinControls.sol (ย่อ)
function _beforeDebit(address _from, uint32 _dstEid, uint256 _amountSentLD) internal whenNotPaused {
    if (isBlacklisted[_from]) revert AccountBlacklisted(_from);
    _outflow(_dstEid, _amountSentLD);                 // rate limit ขาออก
}

function _quarantines(address _to, uint32 _srcEid, uint256 _amountLD) internal whenNotPaused returns (bool) {
    _inflow(_srcEid, _amountLD);                      // คืนโควตาให้ path
    if (!isBlacklisted[_to]) return false;
    quarantined[_to] += _amountLD;
    totalQuarantined += _amountLD;
    emit Quarantined(_to, _srcEid, _amountLD);
    return true;                                      // ไม่ revert: message ถึงตามปกติ
}

// UsdcOFT.sol
function _credit(address _to, uint256 _amountLD, uint32 _srcEid) internal override returns (uint256) {
    if (_quarantines(_to, _srcEid, _amountLD)) {
        _mint(address(this), _amountLD);              // มีหลักประกัน แต่ใช้ไม่ได้
        return _amountLD;
    }
    return super._credit(_to, _amountLD, _srcEid);
}

function _update(address _from, address _to, uint256 _value) internal override {
    if (isBlacklisted[_from]) revert AccountBlacklisted(_from);
    if (isBlacklisted[_to]) revert AccountBlacklisted(_to);
    super._update(_from, _to, _value);
}

ทางแก้คือเพดานยอดที่รับได้ต่อเชนต้นทางต่อ window ใน StablecoinControls (ใช้ร่วมกันทั้ง UsdcOFT และ UsdcAdapter)

  • เกินเพดาน → กักทั้งก้อน ด้วย quarantine เดิม ไม่ revert (message ไม่ค้าง) และไม่แบ่งจ่าย (ไม่งั้นผู้โจมตีได้ส่วนที่พอดีเพดานทุกครั้ง)
  • ยอดที่ถูกกักไม่กินเพดานและไม่คืนโควตาขาออก ไม่งั้น message ปลอมจะเติมโควตาให้ผู้โจมตีถอนออก
  • owner ปล่อยด้วย releaseQuarantined หลังตรวจแล้ว เช่นการโอนก้อนใหญ่ที่ถูกต้อง
  • window = 0 หมายถึงไม่มีเพดาน (ค่าเริ่มต้น) ส่วน limit = 0 หมายถึงกักทุกอย่าง
function _quarantines(address _to, uint32 _srcEid, uint256 _amountLD) internal whenNotPaused returns (bool) {
    if (isBlacklisted[_to]) { _hold(_to, _srcEid, _amountLD); return true; }
    InboundCap storage cap = inboundCaps[_srcEid];
    if (cap.window != 0) {
        uint256 used = _inboundUsed(cap);                  // ลดลงเป็นเส้นตรงตามเวลา
        uint256 available = used >= cap.limit ? 0 : cap.limit - used;
        if (_amountLD > available) {
            _hold(_to, _srcEid, _amountLD);               // กักทั้งก้อน ไม่ revert
            emit InboundCapExceeded(_to, _srcEid, _amountLD, available);
            return true;
        }
        cap.used = used + _amountLD;
        cap.lastUpdated = uint64(block.timestamp);
    }
    _inflow(_srcEid, _amountLD);                          // คืนโควตาขาออกเฉพาะยอดที่จ่ายจริง
    return false;
}

7.2 เงื่อนไขความปลอดภัยของ composer

UsdcDepositComposer รับ USDC.lz ที่ bridge มาแล้วฝากเข้า vault (ERC-4626) ให้ผู้รับ เงื่อนไขที่ต้องมีครบคือ

  1. เรียกได้เฉพาะ endpoint (OnlyEndpoint)
  2. รับเฉพาะ compose ที่ queue โดย UsdcOFT ของเรา (UntrustedOApp) เพราะ OApp ใดๆ บน endpoint เดียวกันก็ queue compose หาเราได้ และอ้างยอดเท่าไหร่ก็ได้
  3. ฝากไม่สำเร็จต้อง refund ไม่ใช่ revert เพราะ lzCompose ที่ revert จะทำให้เงินค้างใน composer
  4. ถ้า refund ก็ไม่สำเร็จ (เช่นผู้รับถูก blacklist) ให้ park ไว้ให้ owner ตัดสิน เงินไม่หาย
function lzCompose(address _from, bytes32 _guid, bytes calldata _message, address, bytes calldata)
    external payable override
{
    if (msg.sender != endpoint) revert OnlyEndpoint(msg.sender);
    if (_from != oft) revert UntrustedOApp(_from);

    uint256 amount = OFTComposeMsgCodec.amountLD(_message);
    // [nonce 0..8][srcEid 8..12][amountLD 12..44][composeFrom 44..76][app payload 76..]
    address beneficiary = abi.decode(_message[PAYLOAD_OFFSET:], (address));

    try vault.deposit(amount, beneficiary) returns (uint256 shares) {
        emit Deposited(_guid, beneficiary, amount, shares);
    } catch {
        try IERC20(oft).transfer(beneficiary, amount) returns (bool ok) {
            if (ok) { emit Refunded(_guid, beneficiary, amount); return; }
        } catch {}
        parked[beneficiary] += amount;
        emit Parked(_guid, beneficiary, amount);
    }
}

async function tick(src) {
  const latest = await src.pub.getBlockNumber();
  const safe = latest - BigInt(src.confirmations);   // รอ finality ของต้นทาง
  for (let start = from; start <= safe; start += 1_000n) {
    const jobs = await src.pub.getLogs({ address: dvnOn(src), event: jobAssignedEvent, ... });
    const assigned = new Set(jobs.map((j) => keccak256(j.args.packetHeader)));
    for (const ev of await scanPacketSent(src, start, end)) {
      if (assigned.has(ev.packet.headerHash)) await attest(src, ev.packet);
      else log(ROLE, `nonce ${ev.packet.nonce}: not assigned to ${DVN_ID}, skip`);
    }
  }
}

  • deposit() คืนเหรียญกลับ ส่วน withdraw() แค่ emit event

  • PotatoNativeAdapter (potato): เกินเพดาน → native ไม่ออกจาก lockbox แต่ถูกบันทึกเป็นยอดกักของผู้รับ และ check-supply หักออกจากยอด lock
  • PotatoOFT (anvil): เกินเพดาน → mint เข้าตัว contract เองเหมือน USDC.lz
  • ปล่อยเงิน: owner เรียก releaseQuarantined ถ้าผู้รับเป็น contract ที่รับ native ไม่ได้ จะ revert CreditFailed แต่เงินยังถูกกักอยู่ owner เลือกผู้รับคนอื่นได้ (ต่างจากตอน lzReceive ที่ message ค้างถาวร)
  • ไม่บังคับ rate limit ขาออก: RateLimiter ที่ยังไม่ได้ตั้งค่ามีเพดาน 0 ซึ่งจะบล็อกการส่งทั้งหมด
contract PotatoNativeAdapter is NativeOFTAdapter, InboundMintCap {
    function _credit(address _to, uint256 _amountLD, uint32 _srcEid) internal override returns (uint256) {
        if (_capHolds(_to, _srcEid, _amountLD)) return _amountLD;  // native อยู่ใน lockbox ต่อ กักไว้ให้ _to
        return super._credit(_to, _amountLD, _srcEid);
    }
}

16.4 IBC client หมดอายุ: เกิดขึ้นจริงระหว่าง workshop

ตอนเริ่มบทนี้เราตรวจ IBC ของ potato แล้วพบว่า light client 07-tendermint-0 เป็น Expired ส่วน channel-0 ยังเป็น STATE_OPEN แต่โอนไม่ได้จริง สาเหตุคือ gaia-local และ Hermes relayer หยุดตั้งแต่ 27 ก.ย. นานกว่า trusting period 14 วัน เมื่อเปิด gaia ขึ้นมาก็พบว่า client ฝั่ง gaia ที่ติดตาม potato หมดอายุเหมือนกัน

ทำไมหมดอายุแล้วอัปเดตต่อไม่ได้: light client เชื่อ validator set ล่าสุดที่รู้จักได้แค่ช่วง trusting period (ต้องน้อยกว่า unbonding period 21 วัน) หลังจากนั้น validator ชุดเก่าอาจถอนเงินที่ stake ไปแล้ว การลงโทษจึงทำไม่ได้ client จึงต้องหยุดเชื่อด้วยตัวเอง

16.5 กู้ด้วย governance

  1. สร้าง substitute client ใหม่ของ counterparty เดิมด้วย Hermes
  2. ยื่น proposal recover-client <subject> <substitute> ซึ่งคัด state ของ substitute ไปใส่ subject client
  3. validator โหวต yes (potato 4 ตัว, gaia 1 ตัว, voting period 30 วินาทีใน localnet)
  4. subject client กลับมา Active ด้วย id เดิม connection, channel และ voucher denom ทุกตัวจึงไม่ต้องเปลี่ยน

Token และ stablecoin

  1. adapter อยู่บน home chain ที่เดียว invariant: locked ≥ minted และแยก "ระหว่างทาง" ออกจาก "mint เกิน" (บท 5)

  3. stablecoin ต้องมี control ตั้งแต่วันแรก: rate limit ทั้งขาออกและขาเข้า, pause, blacklist (แยก role จาก owner) control ฝั่งส่งอย่างเดียวไม่ช่วยเมื่อผู้ยืนยันถูกเจาะ (บท 6, เคส Cysic)

Checklist ก่อนขึ้น production

สถานะ ณ วันจบ workshop รายละเอียดเต็มอยู่ใน docs/production-path.md

เชน potato

ต้องทำเปิด public testnet แล้วตามด้วย mainnet พร้อม RPC สาธารณะที่เสถียร, explorer และ faucet
พร้อมpatch RPC 2 ตัวของ cosmos/evm (ตรวจ upstream ก่อน mainnet แล้วถอด patch ที่ไม่จำเป็น)
ต้องทำแผน upgrade cosmos/evm ผ่าน x/gov โดยไม่ทำให้ IBC และ LayerZero สะดุด

LayerZero (POTATO ↔ EVM)

ต้องยืนยันติดต่อ LayerZero Labs เรื่อง chain integration: deploy EndpointV2, EID ทางการ, executor รองรับ potato
ต้องยืนยันDVN อย่างน้อย 2 รายที่อิสระต่อกันและรองรับ potato
ต้องทำตั้ง lzReceive/lzCompose gas จากการวัดบนเชนจริงต่อเชนปลายทาง (enforced options ของ lab ยังเป็น 100k)
พร้อม (lab)inbound mint cap ของ POTATO (บท 13.5, POTATO v2) ใน production ต้องตั้งเพดานจาก volume จริง
พร้อม (lab)pause และ rate limit ขาออกของ POTATO (บท 13.6, ADR 0007, POTATO v3)
พร้อม (lab)inbound mint cap ของ leg USDC (ADR 0006, USDC v3) ใน production ต้องตั้งเพดานจาก volume จริง
ต้องทำเลิกใช้ contract ของ lab (EndpointV2/ULN302 ที่ deploy เอง, LabDVN, LabExecutor, workers)
ต้องทำaudit PotatoNativeAdapter, StablecoinControls และ config ทุก path
พร้อมตั้ง security ราย OApp, pin library, ขั้นตอนเปลี่ยน DVN แบบไม่ให้ message ค้าง
พร้อมowner/delegate เป็น Safe และจัดการ config ด้วย DevTools (พิสูจน์บน testnet)

IBC (POTATO ↔ Cosmos, USDC เข้า)

พร้อมICS-20 + PotatoBridge ทำงานกับ gaia-local, runbook กู้ client (make ibc-recover)
ต้องทำrelayer ≥ 2 operator และ alert ก่อน client หมดอายุ
ต้องทำchannel ไป Injective เพื่อรับ native USDC (CCTP V2) และ allowlist ของ denom ที่ยอมรับ
ต้องทำIBC rate-limit middleware สำหรับ ICS-20

Operations

พร้อมindexer สองเชน, check-supply + audit ด้วย payload hash, playbook ที่ซ้อมแล้ว
ต้องทำalert real-time: FORGED/POISONED, invariant ผิด, message ค้างนาน, client ใกล้หมดอายุ, relayer/DVN หยุด
ต้องทำindex event Quarantined และแสดงใน UI
ต้องทำทางกู้เหรียญที่ค้างใน adapter ที่ปิดแล้ว (ออกแบบไม่ให้เป็นช่องโหว่ใหม่)

อภิธานศัพท์

OApp
Omnichain Application: contract ที่ส่งและรับ message ผ่าน endpoint ของ LayerZero
OFT / OFTAdapter / NativeOFTAdapter
OApp สำเร็จรูปสำหรับ token แบบ mint/burn, lock/unlock ERC-20 เดิม และ lock/unlock native coin (บท 5)
EndpointV2
contract หลักของ LayerZero บนแต่ละเชน immutable เก็บ nonce และเรียก lzReceive
EID
Endpoint ID: รหัสของเชนในเครือข่าย LayerZero (ไม่ใช่ chainId) เช่น Sepolia 40161
SendUln302 / ReceiveUln302
message library ที่ assign งานให้ DVN และ executor (ฝั่งส่ง) และรวบรวมการยืนยันของ DVN (ฝั่งรับ)
DVN
Decentralized Verifier Network: ผู้ยืนยันว่า packet มีอยู่จริงบนต้นทาง ชุด DVN ที่ OApp เลือกคือ security model ของ OApp
Executor
ผู้ส่งของถึงปลายทาง (commitVerification + lzReceive) ปลอม message ไม่ได้
ULN config
confirmations, required/optional DVNs และ threshold ของแต่ละ path (บท 3)
delegate
address ที่ endpoint ยอมให้ตั้ง config ของ OApp แทน owner
options / enforced options
สิ่งที่ผู้ส่งขอ เช่น gas ของ lzReceive / ค่าขั้นต่ำที่ OApp บังคับทุก message
GUID
รหัสไม่ซ้ำของ message แต่ละตัว
payload hash
hash ของ GUID + message ที่ endpoint ปลายทางเก็บไว้หลังยืนยัน ใช้ตรวจว่าของที่ถึงตรงกับที่ส่งจริง
FORGED / POISONED
ปลายทางรับ payload ที่ต้นทางไม่เคยส่ง / ช่อง nonce ถูกใช้กับ payload อื่น ของจริงจึงไม่มีวันถึง (บท 8)
BlockedMessageLib
library ที่ปฏิเสธทุก message ใช้หยุด path ฉุกเฉินโดยไม่ต้องมี pause ใน contract
lzCompose
การเรียกต่อบนปลายทางหลัง lzReceive เป็น tx แยก (บท 7)
lzRead / read channel
การอ่านค่าจากเชนอื่นผ่าน read DVN ใช้ channel 4294967295 และ ReadLib1002
shared decimals / dust
ความละเอียด 6 ตำแหน่งที่ใช้ส่งข้ามเชน / เศษที่ละเอียดกว่านั้นซึ่งยังอยู่ใน wallet ผู้ส่ง
inbound mint cap
เพดานยอดที่ leg จ่ายได้ต่อเชนต้นทางต่อ window ส่วนที่เกินถูกกักทั้งก้อน ใช้ทั้ง USDC และ POTATO ผ่าน InboundMintCap (บท 6.5, 13.5, ADR 0006)
quarantine
การกักเงินที่ส่งมาให้ address ที่ถูก blacklist แทนการ revert (บท 6)
light client / trusting period
ตัวตรวจ consensus ของอีกเชนบน chain ใน IBC / ช่วงเวลาที่ยังเชื่อ validator set ล่าสุดได้ เกินแล้ว client หมดอายุ
MsgRecoverClient
gov message ที่คัด state ของ substitute client ไปใส่ client ที่หมดอายุ
LZBL-1.2
license ของ protocol LayerZero: non-production use เท่านั้นจนถึง 2027-12-14

Binance hot wallet ถูกกวาดได้อย่างไร

ลำดับเหตุการณ์ทางเทคนิคของเหตุการณ์ 29 ต.ค. 2026 สร้างจากข้อมูลบนเชนที่อ่านและ replay เองทั้งหมด ตั้งแต่ผู้โจมตีรับเงินตั้งต้นจาก Tornado Cash ไปจนถึงการแช่แข็งเงิน

เชน ยืนยันจากข้อมูลบนเชน รันซ้ำได้ด้วย script ข่าว มาจากรายงานข่าว ยังไม่ได้ตรวจเอง อนุมาน ข้อสรุปจากหลักฐาน ยังไม่มีการยืนยัน
คำตอบสั้น พื้นฐาน EIP-7702 ผู้เกี่ยวข้อง ลำดับเหตุการณ์ เงินไปไหน เกิดขึ้นได้อย่างไร จุดที่ตรวจจับได้ บทเรียน ทำซ้ำ

คำตอบสั้น: เกิดขึ้นได้อย่างไร

  1. เชน ผู้โจมตีได้ลายเซ็นจริงจาก key ของ hot wallet "Binance 14" ไป 50 ครั้ง เป็น authorization ของ EIP-7702 สำหรับ nonce 50 ค่าที่เรียงติดกัน (ตรวจด้วย cast recover-authority แล้ว ทั้ง 50 ตัวกู้กลับเป็น address ของ Binance 14)
  2. เชน authorization ตัวที่ nonce ตรงทำให้ Binance 14 ซึ่งเป็น EOA ธรรมดา กลายเป็นบัญชีที่รันโค้ดของผู้โจมตี (code เปลี่ยนจาก 0x เป็น 0xef0100‖0x63e8…6fae)
  3. เชน 3 นาที 24 วินาทีต่อมา tx เดียวเรียก sweep() ที่ Binance 14 กวาด 167,464 ETH และ token 63 ตัว โดยไม่ต้องใช้ลายเซ็นของ Binance อีกเลย
  4. เชน เพราะ Binance 14 เป็นผู้สั่งการของ smart wallet อีกตัว (0xEe7a…4055) ผู้โจมตีจึงได้สิทธิ์นั้นไปด้วย และดึง USDC ออกไป 823M
  5. เชน Binance 16 (wallet อีกตัวที่ไม่ได้ถูก delegate) เซ็นและส่ง 28,005.6 ETH ไปให้ผู้โจมตีเอง 24 วินาทีหลังการกวาด
  6. เชน delegation ยังอยู่อีก 226 นาที ผู้โจมตีกลับมากวาดเงินฝากใหม่อีก 9 รอบ ก่อนที่ Binance จะถอน delegation
  7. อนุมาน การที่ wallet สองตัวเซ็นให้ผู้โจมตีด้วย payload คนละแบบ (authorization 7702 และการโอน ETH ปกติ) ชี้ไปที่ระบบที่ขอให้ hot wallet เซ็น (signing pipeline) ถูกควบคุม มากกว่าการที่ smart contract มี bug ส่วนกลไกจริงว่าเข้าถึงระบบเซ็นได้อย่างไร Binance ยังไม่ได้เปิดเผย

พื้นฐานที่ต้องรู้: EIP-7702 เปลี่ยน EOA อย่างไร

ก่อน hardfork Pectra (พ.ค. 2025) บัญชี Ethereum มีสองแบบชัดเจน: EOA ซึ่งไม่มีโค้ดและทำอะไรได้เฉพาะเมื่อ private key เซ็น tx กับ contract ซึ่งมีโค้ดแต่ไม่มี key EIP-7702 เพิ่ม tx แบบใหม่ (type 4) ที่มี authorizationList

  • authorization คือข้อความ (chainId, address, nonce) ที่เจ้าของ EOA เซ็นด้วย key ว่า "ให้บัญชีของฉันรันโค้ดของ address"
  • ใครก็ได้ส่ง tx type 4 ที่มี authorization นั้น ไม่จำเป็นต้องเป็นเจ้าของ EOA (ในเคสนี้ผู้โจมตีเป็นคนส่งและจ่ายค่า gas เอง)
  • authorization จะใช้ได้เฉพาะเมื่อ nonce ตรงกับ nonce ปัจจุบันของ EOA ตอน tx ถูก process ถ้าไม่ตรงจะถูกข้ามเฉยๆ ไม่ทำให้ tx ล้ม
  • เมื่อใช้ได้ code ของ EOA จะเป็น 0xef0100 ‖ address (delegation designator) และอยู่ไปจนกว่าเจ้าของจะเซ็น authorization ใหม่มาเปลี่ยน ใครเรียก EOA นั้นจะไปรันโค้ดของ address โดยมี address(this) เป็น EOA และใช้เงินของ EOA
ผลด้านความปลอดภัย

ลายเซ็นของ authorization ไม่ใช่ลายเซ็นของ tx ระบบเซ็นที่ตรวจเฉพาะ "tx โอนเงินไปที่ไหน เท่าไหร่" อาจไม่รู้ว่าข้อความ keccak256(0x05 ‖ rlp(chainId, address, nonce)) ที่ถูกขอให้เซ็นมีความหมายว่า "ยกบัญชีทั้งบัญชีให้ contract นี้"

  • key ของ Binance 14 เซ็น authorization 50 ตัวให้ contract ของผู้โจมตี
  • Binance 16 เซ็นการโอน 28,005.6 ETH ไปที่ address ของผู้โจมตี
  • ไม่มี smart contract ของ Binance ถูกหลอกด้วย bug ทุกอย่างผ่านการตรวจลายเซ็นและสิทธิ์ตามปกติ
  • ผู้โจมตีเตรียมตัวราว 37 ชั่วโมงนับจากได้เงินตั้งต้น และซ้อมบน mainnet สองรอบ

อนุมาน น่าจะเป็น

  • ผู้โจมตีควบคุมช่องทางที่ส่งคำขอให้ระบบเซ็นของ hot wallet ได้ เพราะได้ลายเซ็นจาก wallet สองตัว คนละรูปแบบ และจำนวนมาก
  • ระบบเซ็นไม่ได้แยกหรือบล็อก payload แบบ authorization ของ EIP-7702 ซึ่งมีความหมายต่างจาก tx โอนเงินโดยสิ้นเชิง

ยังไม่รู้

  • ผู้โจมตีเข้าถึงระบบเซ็นได้อย่างไร (สิทธิ์ภายใน, ช่องโหว่ของซอฟต์แวร์, key หลุด หรือ supply chain)
  • authorization ถูกเซ็นเมื่อไหร่ และ key ของ wallet อื่นได้รับผลกระทบหรือไม่
  • ผู้อยู่เบื้องหลัง (มีนักวิจัยบางรายพูดถึงเกาหลีเหนือ แต่ไม่มีการยืนยันอย่างเป็นทางการ)
สมมติฐานที่หลักฐานไม่สนับสนุน

"bug ใน smart contract": ไม่มี contract ไหนทำงานผิดสเปก "key หลุดดอกเดียว": อธิบายได้ยากว่าทำไม Binance 16 ซึ่งไม่ได้ถูก delegate ก็ส่งเงินให้ผู้โจมตีด้วย ยกเว้นว่า key หลุดหลายดอก

เทียบกับ alert ใน workshop (บท 8.9)

worker ที่ตรวจทุก 3 วินาทีจะเห็น code ที่เปลี่ยนภายใน 1–2 block และระบบที่ตอบสนองอัตโนมัติ (เช่นย้ายเงินออกด้วย key อีกชุด หรือหยุดเส้นทางฝากเงิน) ก็มีเวลามากพอ ถึงตอบสนองไม่ทัน 3 นาทีแรก การถอน delegation ทันทีก็กันเงินฝากและการกวาดซ้ำ 9 รอบหลังจากนั้นได้

บทเรียน

  1. ระบบเซ็นต้องเข้าใจสิ่งที่เซ็น: ปฏิเสธ payload แบบ EIP-7702 authorization (prefix 0x05) จาก hot wallet เสมอ ยกเว้นผ่านขั้นตอนพิเศษ
  2. ตรวจ eth_getCode ของทุก EOA ที่ถือเงินทุก block: ถ้าไม่ใช่ 0x ให้แจ้ง critical และถอน delegation ทันที
  3. อย่าเก็บเงินหลายพันล้านไว้ใน EOA เดียว: ไม่มีเพดานบนเชนเลย tx เดียวเอาออกได้ทั้งหมด ควรใช้ contract ที่มี rate limit หรือ timelock เหมือน control ใน workshop
  4. ลดสิทธิ์ที่ต่อกันเป็นทอด: hot wallet ที่รับเงินฝากไม่ควรเป็นผู้สั่งการของ wallet อื่นที่ถือ USDC อีก 823M
  5. whitelist ปลายทางของการโอนจาก hot wallet: และให้ address ใหม่ต้องรอ (cool-down) ก่อนใช้ได้
  6. stablecoin ที่แช่แข็งได้ช่วยได้จริง: USDT 1.175B และ USDC 823M ใน Exploiter 2 ถูกแช่แข็งแล้ว แต่ ETH ทำไม่ได้

ทำซ้ำ

script อ่านอย่างเดียวทั้งหมดอยู่ใน forensics/binance-2026-10-29/ และต้องใช้ RPC ที่ให้ state ย้อนหลังได้ (ค่าเริ่มต้นคือ eth.drpc.org ตั้งเองได้ด้วย RPC_URL)

cd forensics/binance-2026-10-29
python3 timeline.py        # delegation, authorization 50 ตัว, สถานะ wallet ทีละ block
python3 authorities.py     # กู้ผู้เซ็นของ authorization ทั้ง 50 ตัว
python3 prep.py            # เงินตั้งต้นจาก Tornado และการ deploy contract
python3 attacker_txs.py    # ทุก tx ของผู้โจมตี (การซ้อม → delegate → กวาด → กวาดซ้ำ)
python3 b16.py             # Binance 16 โอนเงินเอง
python3 flows.py <tx>...  # replay tx ด้วย cast run แล้วสรุปการโอน
./replay.sh                # replay การกวาดหลักแบบ trace เต็ม
python3 revoke.py          # เวลาที่ถอน delegation
python3 follow.py && python3 summarise.py   # ทุก tx ของ address ผู้โจมตีหลังการกวาด (~10 นาที)
python3 inflows.py <address>  # ETH ของ address หนึ่งมาจากไหน (ไล่ย้อนทีละทอด)
python3 usdt_trail.py      # USDT 700M ที่หนีออกไปก่อนถูกแช่แข็ง

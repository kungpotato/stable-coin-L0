bamboo Protocol

เอกสารทางเทคนิคสำหรับ bamboo — โปรโตคอลส่งข้อความข้ามเชนแบบ non-custodial, attestation-based สำหรับระบบ stablecoin หลาย issuer หลายเชน

เอกสารนี้สร้างจากซอร์สในไดเรกทอรี bamboo/ (contracts src/, off-chain relay/). สถานะ: v0.1 draft — self-audited lab MVP, ยังไม่ผ่าน independent audit.

Introduction

bamboo เป็น generic cross-chain messaging layer: สัญญาบนเชนหนึ่งส่งข้อความ (payload เป็น bytes อะไรก็ได้) ไปให้แอปบนอีกเชนประมวลผล โดยส่งผ่านตัวกลาง (relay) ที่ ไม่จำเป็นต้องเชื่อถือ — ความถูกต้องถูกบังคับด้วย ลายเซ็นของชุด attester ที่ตรวจสอบบนเชนปลายทาง

Design goals

  • Non-custodial — ตัวกลางไม่มีสิทธิ์ mint/ถือเงิน ปลอมข้อความไม่ได้
  • Accountable trust — ผู้รับรอง (attester) = issuer ที่มี license + ผู้กำกับ ไม่ใช่ validator นิรนาม
  • Generic — token transfer เป็นเพียงแอปตัวอย่าง; แอปใดก็สร้างบน messaging layer ได้
  • Regulator-aligned — มี whitelist, freeze/pause, mint cap, reconciliation hooks

Non-goals

  • ไม่ใช่ trustless light-client bridge (เป็นไปไม่ได้เมื่อเชนปลายทางเป็น black box)
  • ไม่รับประกัน atomic settlement ข้ามเชน (ดู Two Generals)

Quickstart (local)

รัน anvil ↔ anvil พร้อม relay mesh และโอน token ข้ามเชน

# prerequisites: Foundry (anvil/cast/forge), Node.js >= 22, jq

# 1. สอง local EVM
anvil --port 28545 --chain-id 31338 --hardfork prague --block-time 1 &
anvil --port 38545 --chain-id 31340 --hardfork prague --block-time 1 &

# 2. deploy + wire (token, gateway, OFT, attester set, peers, caps, seed)
cd bamboo
A_NAME=anvilA A_RPC=http://localhost:28545 A_ID=1 \
B_NAME=anvilB B_RPC=http://localhost:38545 B_ID=2 ./deploy.sh

# 3. relay mesh (3 attesters + 2 submitters)
cd relay && npm install && cd ..
./run-mesh.sh

# 4. demo: โอน 100 bUSD A->B แล้ว verify supply
./demo.sh

ผลลัพธ์: supply ฝั่ง A ลด 100, ฝั่ง B เพิ่ม 100 (supply รวมคงที่ = burn-and-mint)

Attesterผู้ถือ key ที่เซ็นรับรองข้อความ (issuer / ผู้กำกับ)
Submitter / Relayผู้เดินสาร — เก็บลายเซ็นแล้ว submit ปลายทาง (ไม่ถือ key)
Threshold (N-of-M)จำนวนลายเซ็น attester ขั้นต่ำที่ต้องมี

Logical chain idรหัสเชนเชิงตรรกะที่โปรโตคอลใช้ (ไม่จำเป็นต้องเท่ากับ EVM chainid)

Trust model

ความปลอดภัยตั้งอยู่บน attester set + N-of-M threshold ข้อความจะถูก execute บนปลายทางได้ต่อเมื่อมีลายเซ็น จาก attester ที่ลงทะเบียน ครบ threshold ตัว

บทบาทถือ signing keyทำได้ / ไม่ได้
Attesterใช่ (HSM ใน production)เป็นรากความเชื่อถือ — รับผิดตามกฎหมาย
Submitter/Relayไม่ (เฉพาะ gas key)เดินสารเท่านั้น — ปลอม/mint ไม่ได้ ทำได้แค่ช้า/ดอง (แก้ด้วย redundancy + self-relay)
Owner—admin (ควรเป็น multisig+timelock)
Guardian—pause ฉุกเฉินได้อย่างเดียว (unpause ไม่ได้)

Trust assumptions

  • attester ที่ซื่อสัตย์ < threshold (ถ้า ≥threshold สมคบ → ปลอมได้ แต่ bound ด้วย cap + reconciliation + legal)
  • signing key ของ attester ไม่รั่ว (ลดด้วย HSM + การกระจายผู้เซ็นอิสระ)
  • โค้ดสัญญาถูกต้อง (ต้องผ่าน audit — ยังไม่ได้ทำ)

Messaging layer & apps

Interoperability protocol
  └─ Messaging layer (BambooGateway) — ส่ง arbitrary bytes, verify N-of-M
       └─ Apps (implement IBambooReceiver)
            ├─ BambooOFT       — burn-and-mint token transfer (reference app)
            └─ <your app>      — cross-chain call, governance, ฯลฯ

Gateway ไม่รู้จัก token — มันแค่ส่ง bytes แล้วเรียก bambooReceive() บนแอปปลายทาง ความหมายของ payload เป็นเรื่องของแอป

Message identity (msgId)

msgId คำนวณเหมือนกันทั้งสองเชน ใช้สำหรับ dedup / replay protection

msgId = keccak256(abi.encode(
          uint64  srcChainId,   // logical id เชนต้นทาง
          uint64  dstChainId,   // logical id เชนปลายทาง
          address sender,       // แอปต้นทาง
          address receiver,     // แอปปลายทาง
          bytes32 keccak256(payload),
          uint64  nonce         // per-gateway outNonce
        ))

msgId ไม่ผูกกับ EVM chainid หรือ address ของ gateway — การผูก domain อยู่ที่ "digest ที่เซ็น" (ด้านล่าง)

Signing digest (domain separation)

attester ไม่ได้เซ็น msgId ตรงๆ แต่เซ็น digest ที่ผูกกับ gateway ปลายทาง + EVM chain เพื่อกันการนำลายเซ็นไป replay ข้าม gateway/เชนอื่น

inner  = keccak256(abi.encode(block.chainid, address(gateway), msgId))
digest = keccak256("\x19Ethereum Signed Message:\n32" ‖ inner)   // EIP-191

ฝั่ง off-chain (innerDigest() ใน common.ts) ต้องคำนวณ inner ด้วย EVM chainid + address ของ gateway ปลายทาง แล้วเซ็นแบบ personal_sign

Verification

receiveMessage() ตรวจตามลำดับ:

  1. threshold > 0 (ไม่งั้น revert)
  2. คำนวณ msgId; !processed[msgId] (กัน replay)
  3. recover ทุกลายเซ็นจาก digest(msgId); ต้องเรียง address ascending เข้มงวด (กัน duplicate), ทุกตัว isAttester, reject zero/high-s
  4. นับ ≥ threshold
  5. ตั้ง processed=true (ก่อนเรียกภายนอก) แล้วเรียก receiver.bambooReceive() ใน try/catch

Payload encoding (BambooOFT)

แอป BambooOFT ใช้ payload แบบติด tag: abi.encode(uint8 kind, bytes inner)

kindชื่อinnerทิศ
0TRANSFERabi.encode(address to, uint256 amount)src→dst
1ACKabi.encode(bytes32 origMsgId)dst→src
2CANCELabi.encode(bytes32 origMsgId, address to, uint256 amount, uint64 nonce)src→dst
3CANCEL_ACKabi.encode(bytes32 origMsgId)dst→src
4DELIVERED_NOTICEabi.encode(bytes32 origMsgId)dst→src

Message lifecycle (outbound status)

NONE ─send()─▶ PENDING ─ACK/NOTICE─▶ DELIVERED      (terminal)
                 │
                 └─requestCancel()─▶ CANCEL_REQUESTED ─CANCEL_ACK─┬─▶ REFUNDED        (terminal)
                                                                   └─▶ REFUND_BLOCKED ─resolveRefund()─▶ REFUNDED
ค่าstatusความหมาย
0NONEไม่มีรายการ
1PENDINGส่งแล้ว รอ ACK
2DELIVEREDปลายทาง mint แล้ว (ยืนยันผ่าน ACK/NOTICE)
3CANCEL_REQUESTEDขอ cancel แล้ว รอผล
4REFUNDEDคืนเงินแล้ว
5REFUND_BLOCKEDคืนไม่ได้ (sender ไม่ whitelisted) รอ resolveRefund

Flow: Transfer & ACK

A.send(dst,to,amt)   → token.burnFrom(sender); outbound[msgId]=PENDING; emit MessageSent
   ↓ mesh
B.bambooReceive      → verify threshold → token.mint(to,amt) → gateway.send(ACK)
   ↓ mesh
A.bambooReceive(ACK) → outbound[msgId]=DELIVERED; emit TransferDelivered

Flow: Cancel & refund (two-phase)

A.requestCancel(msgId)  → status=CANCEL_REQUESTED; ส่ง CANCEL ไป B
B รับ CANCEL:
   ├ ถ้า processed(msgId)=true (deliver แล้ว) → ส่ง DELIVERED_NOTICE (A → DELIVERED)
   └ ไม่งั้น → gateway.blockMessage(msgId) [deliver ไม่ได้ตลอดไป] → ส่ง CANCEL_ACK
A รับ CANCEL_ACK:
   ├ sender ยัง whitelisted → mint คืน sender; REFUNDED
   └ ไม่ whitelisted → REFUND_BLOCKED → owner.resolveRefund(msgId, recovery)
No-double-mint invariant: delivery และ block ใช้ flag processed[msgId] ร่วมกัน → เกิดได้อย่างใดอย่างหนึ่ง; CANCEL_ACK ถูกส่งเฉพาะหลัง block สำเร็จ ⇒ refund ⟹ ไม่เคย mint

Flow: Permissionless relay & self-relay

attester (ถือ key) แยกจาก submitter (ไม่ถือ key) — receiveMessage ต้องการแค่ลายเซ็น จึง ใครก็ submit ได้

  • Redundant: รัน submitter หลายตัว แข่งกัน ตัวแพ้เจอ revert "replay" แล้วข้าม
  • Self-relay: ถ้า relay ดับ/เซ็นเซอร์ ผู้ใช้รัน self-relay.ts <msgId> ส่งเองด้วยลายเซ็นที่ publish ไว้

Retail payments (fast-path + netting)

การข้ามเชน ทุกครั้ง ที่จ่ายเงิน (ซื้อผลไม้) ช้า+แพงเกินไป bamboo รองรับ retail ด้วยการ แยกการจ่าย (instant) ออกจากการ settle (batch) — เหมือน Visa authorize ทันที settle ทีหลัง

ชั้น 1 — Payment (instant, local)
  user บน A จ่าย → PSP/operator จ่ายร้านค้าบน B ทันทีจาก FastPayPool (~1s, โอนในเชนเดียว)
  ร้านได้เงินทันที ไม่รอข้ามเชน

ชั้น 2 — Settlement (batch, bamboo)
  payment หลายรายการถูก net รวม → BambooOFT.sendBatch() ส่ง "1 message ต่อรอบ"
  burn รวมจาก A → mint รวมเข้า FastPayPool บน B (เติมเงินที่ pool สำรองจ่ายไป)

ความเร็ว มาจากชั้น 1 (pool สำรองจ่ายก่อน รับความเสี่ยงสั้นๆ — ในโมเดล regulated คือ PSP ที่มี license) · ต้นทุน/throughput มาจากชั้น 2 (ตรวจลายเซ็น + ACK ครั้งเดียวต่อ batch → cost ต่อรายการ ≈ 1/N)

ทดสอบแล้ว: 3 ร้านได้เงินทันทีจาก pool (local) → sendBatch เติม pool กลับ net 0 → เงิน user ย้ายข้ามเชนใน 1 batch · 5 payment ใน 1 message ตรวจลายเซ็นครั้งเดียว

ความเสี่ยง pool จำกัดด้วย: ขนาด pool, per-payout + daily cap, pause, และ operator ที่เป็น PSP มี license (bounded credit risk แบบ card acquirer). ดู src/FastPayPool.sol + fast-pay-demo.sh

Guide: Build an app on the messaging layer

contract MyApp is IBambooReceiver {
    IBambooGateway public gateway;
    mapping(uint64 => address) public peer;

    function doCrossChain(uint64 dst, bytes memory data) external {
        gateway.send(dst, peer[dst], data);          // ส่ง
    }
    function bambooReceive(uint64 src, address sender, bytes32 msgId, bytes calldata payload) external {
        require(msg.sender == address(gateway), "not gateway");
        require(sender == peer[src], "not peer");     // ไว้ใจเฉพาะคู่แฝด
        // ... ประมวลผล payload ...
    }
}
แอปต้อง gate ด้วย msg.sender == gateway และ sender == peer เสมอ มิฉะนั้นใครก็ trigger logic ได้

Security — Threat model

  • Relay compromise → ปลอม/mint ไม่ได้ (ลายเซ็นตรวจ on-chain); ทำได้แค่ดอง → แก้ด้วย self-relay/redundancy
  • Attester < threshold รั่ว → ยังปลอมไม่ได้
  • Attester ≥ threshold สมคบ/รั่ว → ปลอมได้ แต่ bound ด้วย per-transfer/daily cap + guardian pause + reconciliation + legal
  • Contract bug → ไม่กันด้วยฟีเจอร์ ต้อง audit + formal verification
  • Two Generals → ไม่รับประกัน atomic แต่ safety (ถ้า B mint = A อนุมัติจริง) = 100%; liveness กู้ได้ด้วย retry/self-relay/refund

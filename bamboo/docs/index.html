cross-chain messaging / interoperability protocol

🎋 bamboo

โปรโตคอลส่งข้อความข้ามเชนแบบ non-custodial + attestation-based สำหรับระบบ THB stablecoin หลาย issuer หลายเชน — ส่ง payload อะไรก็ได้ข้ามเชน โดยตัวกลาง (relay) ปลอม/ขโมยไม่ได้ และ token transfer เป็นเพียง "แอปตัวแรก" บน messaging layer

ภาพรวม Trust model สถาปัตยกรรม ส่วนประกอบ Flows ความปลอดภัย Setup API กันการแฮก Production

1. ภาพรวม — bamboo ทำอะไรได้

bamboo คือ generic cross-chain messaging layer: smart contract บนเชน A ส่งข้อความ (bytes อะไรก็ได้) ไปเรียกแอปบนเชน B ได้ ผ่านตัวกลาง (relay) ที่ ไม่ต้องเชื่อถือ เพราะความถูกต้องถูกค้ำด้วยลายเซ็นของ "attester set" ที่ตรวจสอบบนเชนปลายทาง

📨 Generic messaging
ส่ง arbitrary bytes payload ข้ามเชน — แอปไหน implement IBambooReceiver ก็รับได้
💵 Token transfer (OFT)
burn-and-mint ข้ามเชน (ไม่ wrap) — เป็นแอปตัวแรกบน messaging layer
🔁 Two-way ACK
ปลายทางส่ง receipt กลับ → ต้นทางรู้ว่า delivered → reconciliation + ตรวจจับ stuck
↩️ Safe refund
cancel transfer ที่ค้างได้อย่างปลอดภัย (two-phase) โดยไม่เสี่ยง double-mint
🌐 Permissionless relay
ใครก็ส่ง message ได้ (self-relay) → relay ดับ/เซ็นเซอร์ก็ไม่ทำเงินติด
🛡️ Issuer เก็บ token เดิม
ไม่ต้องใช้ token ของเรา — grant minter role ให้ gateway, เก็บ proxy/upgradability/controls
บริบท: ออกแบบสำหรับ 3 issuer ที่มี license จาก ธปท. แต่ละรายมีเชนของตัวเอง — ต้องการ interoperability ที่ regulator ยอมรับ (verifier = issuer ที่รับผิดตามกฎหมาย ไม่ใช่ validator นิรนามแบบ public bridge)

2. Trust model — ทำไมถึงปลอดภัย

หัวใจคือ attester set + N-of-M threshold: ข้อความจะถูก execute บนปลายทางได้ก็ต่อเมื่อมี ลายเซ็นจาก attester ที่ลงทะเบียนไว้ครบ threshold ตัว

บทบาทถือ key?ทำอะไรได้ / ไม่ได้
Attester (issuer + BOT)✅ signing keyเซ็นรับรองข้อความ — เป็นที่มาของความเชื่อถือ (ในระบบจริง = issuer ที่มี license รับผิดตามกฎหมาย)
Relay / Submitter (เรา / ใครก็ได้)❌ แค่ gas keyเดินสาร + submit — ปลอม/ขโมย/mint เองไม่ได้ ทำได้แค่ช้า/ดอง (ซึ่งแก้ด้วย redundancy)
Dest gateway—ตรวจ threshold signatures + replay ก่อน execute
เทียบ LayerZero/Wormhole: โครงเดียวกัน (verifier set + threshold) ต่างที่ ใครอยู่ใน set — ของ bamboo = issuer ที่มี license + BOT (accountable) ไม่ใช่ DVN/guardian ภายนอก

Burn-and-mint (ไม่ wrap)

การโอน token ใช้ burn ที่ต้นทาง + mint ที่ปลายทาง → supply รวมทุกเชนคงที่ 1:1 เสมอ ไม่มี wrapped token (ซึ่ง ธปท. เตือนเรื่อง bridging/wrapping ออกนอกขอบเขตกำกับ)

5. Message flows

5.1 Transfer + ACK

A.send(dst,to,amt)   → burnFrom(sender), outbound[msgId]=PENDING, emit MessageSent
   ↓ mesh
B.bambooReceive      → verify threshold → mint(to,amt) → ส่ง ACK(msgId) กลับ
   ↓ mesh
A.bambooReceive(ACK) → outbound[msgId]=DELIVERED  (isDelivered(msgId)=true)

tested ส่ง 100 A→B → B mint → ACK กลับ → A.isDelivered=true · supply รวมคงที่

5.2 Safe cancel + refund (two-phase, กัน double-mint)

A.requestCancel(msgId)   → status=CANCEL_REQUESTED, ส่ง CANCEL ไป B
B รับ CANCEL:
   • ถ้า B.processed(msgId)=true (deliver แล้ว) → ส่ง DELIVERED_NOTICE กลับ (แก้สถานะ A เป็น DELIVERED)
   • ถ้ายังไม่ deliver → blockMessage(msgId) [ส่ง deliver ไม่ได้ตลอดกาล] → ส่ง CANCEL_ACK กลับ
A รับ CANCEL_ACK:
   • ถ้า sender ยัง whitelisted → mint คืน sender, status=REFUNDED
   • ถ้า sender ถูก de-whitelist → status=REFUND_BLOCKED → owner ใช้ resolveRefund(msgId, recovery)
Invariant ความปลอดภัย: deliver กับ block ใช้ flag processed[msgId] ตัวเดียวกัน → เกิดได้แค่ อย่างใดอย่างหนึ่ง; CANCEL_ACK ถูกส่งเฉพาะหลัง block สำเร็จ → refund ⟹ ไม่เคย mint → ไม่มีทาง double-mint

tested refund สำเร็จ (sender ได้คืน / recovery ได้เมื่อ blocked) · ส่ง transfer เดิมซ้ำ → ถูก block · B ไม่ขึ้น

5.3 Permissionless / self-relay

attester (ถือ key) แยกจาก submitter (ไม่ถือ key) — receiveMessage ต้องการแค่ "ลายเซ็น" → ใครก็ submit ได้

  • Redundant: submitter หลายตัวแข่งกัน ตัวแพ้เห็น replay แล้วหลบ
  • Self-relay: relay ดับ/เซ็นเซอร์ → user รัน self-relay.ts <msgId> ส่งเอง

tested 2 submitters: ตัวนึง deliver อีกตัว "already delivered"; ปิด submitter หมด → self-relay กู้ได้

6. ความปลอดภัย

ผ่าน self-audit 2 รอบ — รอบ 1 เจอ 13 (แก้หมด), รอบ 2 เจอ 2 medium (แก้แล้ว)

มาตรการป้องกัน
Domain-separated signaturereplay ข้าม gateway/chain (sign digest ผูก chainid + gateway address)
N-of-M threshold + replay guardปลอมข้อความ / ส่งซ้ำ
Finality wait (confirmations)reorg → double-mint
Recovery (retry) + checkpointmessage หาย/ค้างเมื่อ relay ดับ
Threshold guard on attester removalถอด attester จนต่ำกว่า threshold = DoS
Pause + 2-step ownershipฉุกเฉิน / key หลุด (owner = multisig+timelock ในจริง)
Whitelist + daily mint capmint ให้ wallet ที่ไม่ KYC / จำกัดความเสียหาย
Two-phase canceldouble-mint ตอน refund
Refund whitelist check (M-A)คืนเงินให้ sender ที่โดน sanction อัตโนมัติ
ยังเป็น self-audit บน lab — ก่อนแตะเงินจริงต้องมี independent audit + formal verification และ key ต้องอยู่ใน HSM (ตอนนี้อยู่ใน env = lab เท่านั้น)

7. Setup & การใช้งาน

7.1 Prerequisites

  • Foundry (anvil, cast, forge) — ~/.foundry/bin
  • Node.js ≥ 22 (ใช้ --experimental-strip-types รัน .ts ตรงๆ)
  • jq

7.2 รัน anvil ↔ anvil (เร็วสุด, พิสูจน์ protocol)

# 1) สอง anvil
anvil --port 28545 --chain-id 31338 --hardfork prague --block-time 1 &
anvil --port 38545 --chain-id 31340 --hardfork prague --block-time 1 &

# 2) deploy + wire (token, gateway, OFT, attester set, peers, seed)
cd bamboo
A_NAME=anvilA A_RPC=http://localhost:28545 A_ID=1 \
B_NAME=anvilB B_RPC=http://localhost:38545 B_ID=2 ./deploy.sh

# 3) ติดตั้ง relay deps
cd relay && npm install && cd ..

# 4) สตาร์ท relay mesh (3 attesters + 2 submitters)
./run-mesh.sh

# 5) demo: ส่ง 100 bUSD A→B + verify
./demo.sh

ผลที่ควรเห็น: supply ฝั่ง A ลด 100, ฝั่ง B เพิ่ม 100, รวมคงที่ = burn-and-mint

7.3 รัน anvil ↔ potato (เป้าหมายจริง)

potato เป็น cosmos/evm → มี EVM JSON-RPC ที่ :18545 เหมือน EVM ทั่วไป ต่างแค่:

  1. สตาร์ท potato ก่อน: cd ../../potato-chain && make localnet-up (รอ EVM :18545)
  2. relayer key ฝั่ง potato ต้องมี gas — ตั้ง BAMBOO_RELAYER_KEY_POTATO=<key ที่ faucet เติม>
A_NAME=anvil A_RPC=http://localhost:28545 A_ID=1 A_KEY=<anvil dev key> \
B_NAME=potato B_RPC=http://localhost:18545 B_ID=2 B_KEY=<potato funded key> ./deploy.sh

7.5 กู้ message ที่ค้าง (self-relay)

cd relay
BAMBOO_RELAYER_KEY=<funded on dst> node --experimental-strip-types self-relay.ts <msgId>

7.6 Cancel + refund transfer ที่ค้าง

# ต้นทาง (sender หรือ owner)
cast send $OFT "requestCancel(bytes32)" $MSGID --rpc-url $RPC_A --private-key $KEY
# จากนั้น CANCEL / CANCEL_ACK วิ่งผ่าน mesh เอง -> refund คืน sender
# ถ้า refund ถูก block (sender ไม่ whitelisted):
cast send $OFT "resolveRefund(bytes32,address)" $MSGID $RECOVERY --private-key $OWNER_KEY

9. กันการแฮกที่เกิดจริง (hack → defense)

วิเคราะห์เคสจริง 2021–2026 เทียบกับสิ่งที่ bamboo ป้องกัน ⚠️ ความจริง: "กัน 100% ด้วยโค้ด" ทำไม่ได้ — class implementation bug กันได้ด้วย audit เท่านั้น แต่เคสเงินหายเยอะสุด (misconfiguration + ไม่มี damage cap) bamboo ปิดด้วยดีไซน์ได้

เคสสาเหตุdefense ใน bambooสถานะ
Kelp DAO ~$292M (2026)single-verifier (1-of-1 quorum)Min-threshold floor (ห้าม <2) + N-of-Mปิดได้
Ronin $625M · AFX $24Mvalidator key ถูกขโมยถึง quorumper-transfer cap + daily cap + guardian pause + ผู้เซ็นอิสระ/accountable + reconciliationbound ความเสียหาย
Multichain ~$130MMPC key รวมศูนย์non-custodial — relay ไม่มีอำนาจ mint, key กระจายปิดได้
Poly Network $611Mmessage เรียก privileged functiongateway เรียกได้แค่ bambooReceive; admin = owner-only; แอป gate ด้วย peerปิดได้
Wanchain ~$12M (2026)signature reusedomain separation + nonce + replay guardปิดได้
Verus ~$11.6M (2026)ไม่เช็คว่ายอดโอนตรง payoutamount ผูกใน msgId + payloadHash (แก้ไม่ได้)ปิดได้
Nomad $190Mupgrade ตั้ง trusted root = 0ไม่มี single root; threshold>0 บังคับ; gateway ไม่ upgradeablefootgun ไม่มี
Bybit $1.5B (2025)multisig UI หลอกให้เซ็น (blind sign)attester ตรวจ policy ก่อนเซ็น + domain-bound digestลดความเสี่ยง
Wormhole $320M · zkLink · BNB Bridgeimplementation bug ใน verify logicโค้ดเรียบง่าย + ecrecover + guard ครบ — แต่ bug ของตัวเองยังเป็นไปได้ต้อง audit
สรุปซื่อสัตย์: bamboo แข็งที่สุดในเคสเงินหายเยอะสุด (key concentration / single-verifier / privileged-function) และ bound ความเสียหายได้แม้โดนเจาะ (cap + guardian) แต่ pure implementation bug กันได้ด้วย independent audit + formal verification เท่านั้น — bamboo ยังเป็น self-audit บน lab

มาตรการใหม่ที่เพิ่มจากบทเรียนปี 2025–26 (ทดสอบแล้ว): Min-threshold floor, per-transfer/daily cap, guardian emergency pause (owner|guardian pause / owner-only unpause), attester policy check ก่อนเซ็น

10. ยังไม่ได้ทำ (roadmap สู่ production)

  • Independent audit + formal verification + bug bounty
  • Key management จริง: HSM / MPC (ตอนนี้ key ใน env = lab)
